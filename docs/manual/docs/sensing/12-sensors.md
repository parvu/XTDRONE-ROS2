# 12. Sensor configuration

!!! success "Ported and tested"
    Cameras, stereo cameras, RGB-D, 2D/3D lidars, IMU, bumper and ground truth are available.
    Test: `scripts/tests/run_chapter_tests.sh ch12`.

A UAV has two kinds of sensors:

- **sensors PX4 needs** for state estimation: accelerometer, gyroscope, magnetometer, barometer and GPS. With
  Gazebo Harmonic they are simulated by gz systems (IMU, air pressure, NavSat). PX4 reads them through `gz_bridge`;
  PX4 simulates the magnetometer from the GPS position;
- **payload sensors**: monocular, stereo and depth cameras and 2D/3D lidars. They are added to the XTDrone
  vehicle models and published to ROS 2 by `ros_gz_bridge`.

## Sensor sets of the XTDrone models

| Model | Sensors | ROS 2 topics (under `/<type>_<id>/`) |
|---|---|---|
| `iris`, `solo` | IMU, bumper | `imu_gazebo`, `benchmarker/collision`, `ground_truth/odom` |
| `iris_stereo_camera`, `solo_stereo_camera` | stereo camera 752×480, 90° FOV, baseline 0.12 m, 30 Hz | `stereo_camera/left/image_raw`, `.../left/camera_info`, `stereo_camera/right/...` |
| `iris_realsense_camera` | RGB-D camera 640×480, 60° FOV, 20 Hz | `realsense/depth_camera/color/image_raw`, `.../color/camera_info`, `.../depth/image_raw`, `.../depth/points` |
| `iris_downward_camera` | camera 1280×720, 120° FOV, pointing down | `camera/image_raw`, `camera/camera_info` |
| `iris_2d_lidar` | 2D lidar, 512 samples, 360°, 0.1–20 m, 40 Hz | `scan` |
| `iris_3d_lidar`, `iris_3d_gpu_lidar` | 3D lidar, 32 × 512, ±15°, 0.3–30 m, 15 Hz, plus stereo camera | `velodyne_points`, `stereo_camera/...` |
| `typhoon_h480` | CGO3 gimbal camera (yaw/roll/pitch), IMU, bumper | `cgo3_camera/image_raw`, `cgo3_camera/camera_info`; gimbal commands on `gimbal/{yaw,roll,pitch}_cmd` (std_msgs/Float64, rad) |

Every model also has `imu_gazebo` (the 250 Hz IMU that PX4 uses), `benchmarker/collision` (chapter 44) and
`ground_truth/odom` (chapter 15).

Differences from Gazebo Classic:

- the 2D lidar runs at 40 Hz instead of 500 Hz, because a GPU-rendered lidar at 500 Hz is too expensive;
- the 3D lidar is published as `/<type>_<id>/velodyne_points` instead of the global `/velodyne_points`;
- the frame IDs are the Classic `frameName`s: `stereo_camera_frame`, `depth_camera_base`, `camera_link`,
  `laser_2d`, `laser_3d`, `cgo3_camera_optical_frame`.

## How a sensor is added

In Gazebo Classic, a sensor was a separate model (e.g. `stereo_camera`) included in the vehicle SDF with a joint,
and a `gazebo_ros` plugin published the topic. In Gazebo Harmonic:

1. the sensor is an SDF `<sensor>` in a link of the vehicle model. The Sensors system of the world (`gz-sim-sensors-system`)
   renders it and publishes it on gz-transport, on a topic scoped by world, model, link and sensor:
   `/world/<world>/model/<vehicle>/link/<link>/sensor/<sensor>/image`;
2. `ros_gz_bridge` republishes that topic as a ROS 2 topic. The launch file configures one bridge per vehicle
   from the file `xtdrone_bridge.yaml` that sits next to each model.

The XTDrone models are generated by `ros2/xtdrone_gz/scripts/generate_vehicle_models.py`. Each one includes a
PX4 airframe model with `<include merge="true">` and adds sensor *kits*. Here is the stereo kit as generated
into `models/iris_stereo_camera/model.sdf`, shortened:

```xml
<model name="iris_stereo_camera">
  <include merge="true"><uri>model://x500</uri></include>
  <link name="stereo_camera_link">
    <pose relative_to="base_link">0.12 0 0.03 0 0 0</pose>
    ...
    <sensor name="left" type="camera">
      <pose>0 0.06 0 0 0 0</pose>
      <update_rate>30</update_rate>
      <gz_frame_id>stereo_camera_frame</gz_frame_id>
      <camera>
        <horizontal_fov>1.5708</horizontal_fov>
        <image><width>752</width><height>480</height><format>R8G8B8</format></image>
        <clip><near>0.1</near><far>300</far></clip>
      </camera>
    </sensor>
    <sensor name="right" type="camera"> ... <pose>0 -0.06 0 0 0 0</pose> ... </sensor>
  </link>
  <joint name="stereo_camera_link_joint" type="fixed">
    <parent>base_link</parent><child>stereo_camera_link</child>
  </joint>
</model>
```

and the matching `xtdrone_bridge.yaml` entry:

```yaml
- gz_topic: /world/{world}/model/{name}/link/stereo_camera_link/sensor/left/image
  ros_topic: stereo_camera/left/image_raw
  ros_type: sensor_msgs/msg/Image
  gz_type: gz.msgs.Image
```

## Add your own sensor set

1. Add a kit function to `generate_vehicle_models.py`, following `kit_stereo_camera` or `kit_2d_lidar`. It returns
   the SDF of the sensor link and its bridge entries.
2. Add a vehicle to the `VEHICLES` table, e.g. `"iris_my_sensors": (QUAD, ["my_kit", "imu_gazebo", "bumper"])`.
   The model name must start with the vehicle type (`iris_`).
3. Regenerate the models and rebuild: `python3 ros2/xtdrone_gz/scripts/generate_vehicle_models.py && colcon build`
   in the workspace (or run `scripts/build_xtdrone_ros2.sh`).
4. Launch with `vehicles:=iris_my_sensors`.

Sensor topics are bridged *lazily*: Gazebo still renders the sensor, but the bridge converts messages only
while a ROS 2 node subscribes. To save rendering time, use models without the sensors you do not need.
